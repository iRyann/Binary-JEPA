Pour alimenter l'architecture JEPA, la donnée ne peut être ni une simple retranscription syntaxique (assembleur) ni un graphe monolithique (CFG).
Nous avons forgé une donnée hybride : des séquences comportementales extraites par parcours statique (Bag-of-Paths), traduites en micro-opérations mathématiques (VEX IR) et jalonnées de concepts systèmes (Tokens API).
Une fois numérisée via un vocabulaire strict incluant les jetons de masquage (<MASK>), cette donnée permet à JEPA d'apprendre la dynamique d'exécution d'un programme comme on apprend la loi physique d'un monde : en prédisant l'état des zones masquées à partir du contexte visible.

### Section 3.x : Pipeline de Pré-traitement

#### 3.x.1 Lifting vers la Représentation Intermédiaire VEX IR

La première étape consiste à abstraire le binaire ELF64 de son ISA (Instruction Set Architecture) native. Nous utilisons le framework **angr** pour charger le binaire en mémoire (`auto_load_libs=False`, sans résolution des dépendances dynamiques) et construire un **Graphe de Flot de Contrôle** (CFG) par analyse rapide (`CFGFast`, mode normalisé). Angr s'appuie en interne sur **libVEX**, le moteur de lifting de Valgrind, pour traduire chaque bloc de base x86-64 en **IR VEX** : une représentation fonctionnelle indépendante de l'architecture, composée d'instructions atomiques opérant sur des registres temporaires (`t0`, `t1`, ...). Ce choix confère une invariance architecturale native au pipeline : le même code de tokenisation s'applique sans modification à un binaire ARM ou MIPS.

#### 3.x.2 Extraction du Bag-of-Paths par DFS Randomisé

Plutôt que de travailler sur le CFG global — dont la taille peut rendre toute manipulation intractable — nous opérons **fonction par fonction**. Pour chaque fonction identifiée dans le CFG (en excluant les stubs PLT, les simprocédures angr et les appels système directs), nous construisons le sous-graphe orienté de ses blocs de base et nous y appliquons un **parcours en profondeur (DFS) randomisé** pour générer un ensemble de chemins d'exécution plausibles.

Les contraintes imposées au parcours sont les suivantes :
- **Maximum 500 chemins** par fonction, pour borner le temps de calcul sur les fonctions très ramifiées.
- **Maximum 50 blocs** par chemin, pour éviter les chemins dégénérés qui ne représentent plus aucun flux d'exécution réel.
- **Acyclicité stricte** : un bloc déjà visité dans la branche courante ne peut être revisité (prévention des boucles infinies dans le DFS).

Chaque chemin produit constitue une **trace d'exécution linéaire** : une séquence ordonnée de blocs de base, représentative d'un comportement potentiel de la fonction. L'ensemble de ces traces forme le **Bag-of-Paths** (BoP) de la fonction.

#### 3.x.3 Tokenisation Sémantique : VEX IR et Concepts Systèmes

Chaque bloc de base dans un chemin est converti en une séquence de tokens discrets. Le lifting VEX est mis en cache par adresse de bloc pour éviter toute redondance de calcul lorsqu'un même bloc apparaît dans plusieurs chemins distincts.

**Tokenisation des instructions VEX.** Chaque statement VEX est converti selon sa nature :

| Statement VEX | Token produit |
|---|---|
| `Ist_WrTmp` avec données `Iex_Load` | `VEX_LOAD` |
| `Ist_WrTmp` avec données `Iex_Get` | `VEX_REG_READ` |
| `Ist_WrTmp` avec données `Iex_Const` | `VEX_CONST` |
| `Ist_WrTmp` avec opération binaire `op_AddXX` | `VEX_OP_ADD` |
| `Ist_WrTmp` avec toute opération `op_FOO` | `VEX_OP_FOO` (3 premiers chars normalisés) |
| `Ist_Store` | `VEX_STORE` |
| `Ist_Put` | `VEX_REG_WRITE` |
| `Ist_Exit` | `VEX_EXIT_COND` |
| Bloc non-liftable | `<UNLIFTABLE>` |

Les `Ist_IMark` (marqueurs d'adresse machine) sont systématiquement ignorés car ils ne portent aucune sémantique comportementale.

**Jeton terminal : appels système et API.** Chaque bloc se conclut par un jeton de terminaison qui capture l'intention de haut niveau du transfert de contrôle sortant :
- Si le bloc cible un **stub PLT ou une simprocédure angr** (appel de bibliothèque standard : `malloc`, `printf`, `fopen`...), le jeton est `<API_NOM>` — par exemple `<API_MALLOC>` ou `<API_PRINTF>`.
- Si le bloc aboutit à un **appel système** (`read`, `write`, `mmap`...), le jeton est `<SYSCALL_NOM>`.
- Sinon, le jeton reflète le **jumpkind VEX** du bloc : `JK_CALL` (appel de fonction interne), `JK_RET` (retour), ou `JK_BORING` (saut inconditionnel).

Ce mécanisme est central : il ancre les séquences d'opérations bas-niveau dans des concepts systèmes reconnaissables, donnant au modèle des points de repère sémantiques stables indépendants de l'optimisation compilateur.

#### 3.x.4 Construction du Vocabulaire

Le vocabulaire est construit en deux passes sur le corpus de fichiers JSONL produits par l'étape précédente :

1. **Comptage en flux** (_streaming_) de la fréquence de chaque token sur l'ensemble du corpus, sans chargement en mémoire de la totalité des données.
2. **Filtrage par fréquence minimale** (`min_freq = 2`) pour éliminer les tokens hapax, issus de fonctions exotiques ou d'artefacts de lifting.
3. **Attribution des identifiants** : les trois tokens spéciaux reçoivent des identifiants fixes (`<PAD>` → 0, `<UNK>` → 1, `<MASK>` → 2) ; les tokens du corpus sont classés par fréquence décroissante.

Le vocabulaire final compte **371 entrées**, dont les tokens spéciaux, les opérateurs VEX, les jetons de contrôle de flot (`JK_*`) et les tokens API/syscall les plus fréquents. Cette taille réduite est délibérée : elle contraint le modèle à n'opérer que sur des concepts observés dans le corpus d'entraînement, en rabattant toute nouveauté sur `<UNK>`.

#### 3.x.5 Format de Sortie

L'encodeur de chaque binaire produit un fichier **JSON** structuré par fonction puis par chemin :

```
{
  "<adresse_fonction>": [
    "<embedding_chemin_1_sérialisé_base64>",
    "<embedding_chemin_2_sérialisé_base64>",
    ...
  ],
  ...
}
```

Chaque embedding est un vecteur flottant de dimension 256, aplati, normalisé L2, puis sérialisé via `pickle` et encodé en Base64. Ce format permet une comparaison directe des représentations entre deux binaires sans réinférence, et constitue le point d'entrée du pipeline d'évaluation (scripts 3 et 4).
